# «Будущее 2.0» — целевая архитектура данных

Проектная работа одиннадцатого спринта курса «Архитектор ПО». Цель — за год перейти от центрального DWH на SQL Server 2008 к облачной доменной платформе данных и запустить портал самообслуживания.

Ключевое ограничение: медицинские карты, истории болезни и результаты исследований **не попадают** в аналитическую витрину. Они остаются в изолированном медицинском контуре и используются только в операционных медицинских и ИИ-сценариях.

## Состав работы

- `Task1` — C4 Container целевой системы, анализ и приоритизация проблем.
- `Task2` — границы доменов, DFD и обоснование потоков данных.
- `Task3` — технологический радар, годовой роадмап и бизнес-обоснование.
- `Task4` — компонентная схема IaaS, Terraform-конфигурация и результат проверки.
- `diagrams/generate.py` — воспроизводимая генерация SVG-диаграмм из версионируемых описаний.

## Архитектурные принципы

1. Домен владеет операционными данными, контрактами и дата-продуктами; центральная команда даёт платформу и guardrails.
2. Междоменная интеграция идёт через версионируемые API и события, а не через чужие таблицы.
3. Операционная нагрузка отделена от аналитической; отчёты читают Lakehouse, а не боевые БД.
4. Доступ выдаётся по принципу least privilege: OIDC, MFA, RBAC + ABAC, строковые/колоночные политики, аудит всех запросов и выгрузок.
5. Миграция поэтапная: CDC/anti-corruption layer, параллельная сверка отчётов, подоменное переключение и обратимый rollback.

## Проверка

```bash
python3 diagrams/generate.py --check
terraform -chdir=Task4 fmt -check
terraform -chdir=Task4 init -backend=false
terraform -chdir=Task4 validate
```
