# Обоснование Terraform-конфигурации

## Цель проекта

Конфигурация — минимальный IaaS-срез пилота портала самообслуживания. Он доказывает автоматизацию сети, дисков, VM, правил доступа, NAT и первичной конфигурации. Это не production-топология: в целевой среде потребуются минимум две зоны, private backends, ingress/load balancer, managed KMS, удалённый state и модули.

## Выбор ресурсов

| Ресурс | Выбор | Обоснование |
|---|---|---|
| VM | 2 vCPU, 20% core fraction, 2 GiB RAM, preemptible | достаточно для Nginx health page и проверки cloud-init; минимальная цена одноразового пилота |
| Boot disk | 10 GiB `network-hdd`, `auto_delete` | размер для Ubuntu 22.04 и Nginx; удаляется с VM |
| Data disk | 10 GiB `network-hdd`, отдельный resource | демонстрирует независимый lifecycle данных и подключение диска; для пилота также удаляется |
| VPC/Subnet | отдельная сеть, `/24` | изоляция от других workload и достаточный адресный запас для пилота |
| Security Group | HTTP, опциональный SSH, egress | SSH по умолчанию закрыт; административные CIDR нужно передать явно |
| NAT | публичный адрес только для demo VM | нужен для установки пакетов и видимой проверки health page; production-бэкенды будут private |

## Почему декларативный подход

Terraform описывает желаемое состояние, а не последовательность ручных кликов. Провайдер сравнивает state с облаком, строит граф зависимостей и выполняет только нужную дельту. Это даёт:

- один результат в dev/test/prod при разных значениях переменных;
- code review и аудируемую историю изменений;
- раннее обнаружение ошибок через `fmt`, `validate`, `plan` и policy checks;
- идемпотентность: повторный `plan` после `apply` не должен создавать дубли;
- быстрое восстановление среды и горизонтальное масштабирование через модули/`for_each`;
- контроль drift и запрет неучтённых ручных изменений.

## Развитие до production

1. Вынести reusable modules `network`, `compute`, `security`, хранить state в версионируемом объектном хранилище с блокировкой.
2. Разместить private backends минимум в двух зонах, добавить L7 load balancer, health checks и autoscaling.
3. Заменить публичную VM на private subnet + NAT Gateway; администрировать через bastion/SSM-подобный сервис.
4. Включить KMS-шифрование дисков, managed secrets, WAF, vulnerability scanning и policy-as-code.
5. Настроить backup policy, межзонное восстановление, DR game day и SLO-based alerting.
